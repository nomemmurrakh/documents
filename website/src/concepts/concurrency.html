Concurrency

The document API is synchronous and non-suspending. get(), set(), update(), delete(), exists(), and every field delegate are plain function calls. None of them are suspend functions, and none of them need a coroutine scope. MMKV is memory-mapped, so a read or a write is a memory operation and not disk I/O. There is nothing to wait for.

// no coroutine scope needed for any of these:
note.set(Note(title = "Pick up milk"))
val current = note.get()
note.update(Note::done, true)

Writes are serialized per document

Every write to a document goes through a lightweight lock. The lock does not suspend, and it is not a coroutine Mutex. Because it never suspends, it works safely in plain synchronous code and cannot block a coroutine dispatcher in a way that starves other coroutines.

The lock is what makes a multi-field update { current -> ... } atomic. Reading the current value and writing the new one happen as one uninterrupted step, so a concurrent reader never sees a half-applied update.

The lock belongs to the document's store, not to the Document object you hold. All instances of the same document share it. If two instances update the same document at the same time, one update runs after the other, and neither is lost.

Internally, each store has a fixed set of 64 locks. The library picks one by the document's key, and creates it only when it is first needed. Different documents normally get different locks and never wait for each other. Rarely, two unrelated documents map to the same lock, and then their writes take turns.

What the dispatcher controls

Only the collection of flow() and stateFlow() runs on a configurable dispatcher. It is Dispatchers.Default unless you change it, because reading and decoding a value for each change is CPU work (see Reactivity Model). The dispatcher only affects how a Flow is collected. The document operations themselves stay synchronous, whichever dispatcher your code is running on.
