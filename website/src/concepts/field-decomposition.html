Field Decomposition

A document is never stored as one serialized blob. Each top-level field becomes its own MMKV entry, stored under a key of the form {document}::{field}:

// Note(title = "Pick up milk", body = "2%, not whole", done = false)
// stored as:
note-1::title -> bytes
note-1::body  -> bytes
note-1::done  -> bytes

The :: separator is reserved for this purpose. That is why a document key that contains it is rejected. See Opening Documents.

Why decompose

Decomposition is what makes field-level reactivity and cheap single-field writes possible. update(prop, value) and field delegates each touch exactly one stored key. That is a single putBytes or getBytes call, no matter how many other fields the document has. Nothing else is read or encoded again.

update { current -> ... } works differently. It reads and then writes the whole document. Every field is decoded on the read, and every field is encoded and written again on the write, even when the builder changes only one of them. See Read & Write for when to use each form, and Benchmarks for the measured cost difference between the two.

Nested types

A field whose type is itself a @Serializable object is stored as a single serialized value under that field's key. Examples are a Player inside a save file or an address inside a user profile. This holds at any nesting depth. In v1, nested types are not split up further. Only top-level fields get their own key.

How fields are discovered

The library finds each type's fields through kotlinx.serialization's SerialDescriptor, never through reflection. That keeps it working the same way on Kotlin/Native (iOS) as on the JVM. A custom encoder and decoder write and read each element under its own {doc}::{field} key, instead of using one shared output buffer.

Each field is also where a decoration attaches, if one is configured. A field has one key and one wrap and unwrap pair.
