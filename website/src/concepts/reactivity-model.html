Reactivity Model

MMKV has no built-in way to listen for changes, so reactivity in Documents is handled entirely inside your process, on top of MMKV.

The change bus

Each store has one change bus. The default store has one, and so does every named collection. The bus is a stream of events that lives in memory inside your process. After every committed write or delete, the library puts the key of the affected document on the bus.

A call to document.flow() listens to the bus and reacts only to events for its own key. When one arrives, it reads the document again and emits the fresh value. Emissions are conflated, which means a burst of quick writes does not pile up redundant emissions. The first value is emitted as soon as collection starts, before any new write has happened.

note.flow().collect { current ->
    // runs once right away with the current value, then again after every committed write
}

fieldFlow(prop, default) narrows this down to a single field. A change to a sibling field never triggers it. See Field Delegates.

Several instances of the same document

The bus belongs to the store, not to the Document object you hold. Every instance opened on the same store uses the same bus. So a write through any instance reaches flow(), stateFlow(), and fieldFlow() on all the others.

This works no matter how the instances were created. They can come from dependency injection, from repeated calls to Documents.document(...), or from separate calls to Documents.collection(name) with the same name.

val reader = Documents.document<Note>("note-1")
val writer = Documents.document<Note>("note-1")

reader.flow().collect { current ->
    // runs when the write below commits, even though it went through a different instance
}

writer.set(Note(title = "Pick up milk"))

Collections are separate stores. The same document key in two collections with different names is two unrelated documents, and a write to one does not notify the other. Each call to Documents.inMemory() also creates its own isolated store.

Not cross-process

The change bus only exists inside one process, so changes made by another OS process are not detected. A write from another process never shows up as an emission on this bus.

This matches the single-process rule that applies to storage in general. Both the storage and the reactivity are designed for one process that owns each store.
