Decorations

A decoration is a transform from bytes to bytes. It is applied to one field's value after that value has been encoded as CBOR, and it sits between a Document<T> and the storage layer underneath it. It is the mechanism behind FieldDecorator. See Field Decorators for how to attach one.

The interface

interface FieldDecorator {
    fun wrap(fieldName: String, bytes: ByteArray): ByteArray
    fun unwrap(fieldName: String, bytes: ByteArray): ByteArray
}

wrap runs on every write, right before the encoded bytes reach storage. unwrap runs on every read, right after the bytes come back from storage and before they are decoded.

fieldName is the field's own name, such as "title" for Note::title. It is never a raw storage key. A decorator can single out one field with a check like if (fieldName == Note::title.name) ....

Why reads go in the opposite order

When you configure more than one decorator, a write passes through the list from left to right, and a read passes through it from right to left:

decorators.fold(bytes) { acc, decorator -> decorator.wrap(fieldName, acc) }        // write
decorators.foldRight(bytes) { decorator, acc -> decorator.unwrap(fieldName, acc) } // read

Think of each decorator as a layer wrapped around the bytes. The last decorator to wrap on a write is the outermost layer, so it has to be the first one removed on a read. Reversing the list on the read side is what makes unwrap undo wrap correctly for any number of decorators.

This also means the order you choose matters. With listOf(Compress, Encrypt), the bytes are compressed first and the compressed result is encrypted. On a read, the data is decrypted first, and then decompressed. If you reversed the pair, the library would try to compress bytes that are already encrypted. Encrypted bytes look random, so they do not shrink.

A sketch of encryption as a decoration

Encryption fits this shape well. wrap encrypts the plaintext bytes, and unwrap decrypts them again. Here is a minimal sketch:

class EncryptingDecorator(private val cipher: Cipher) : FieldDecorator {
    override fun wrap(fieldName: String, bytes: ByteArray): ByteArray =
        cipher.encrypt(bytes, associatedData = fieldName.encodeToByteArray())

    override fun unwrap(fieldName: String, bytes: ByteArray): ByteArray =
        cipher.decrypt(bytes, associatedData = fieldName.encodeToByteArray())
}

Passing fieldName as associated data ties each ciphertext to its own field. If a value is copied from one field's storage key to another's, it fails to decrypt. It does not silently succeed with the wrong field's data. See Session & User State for a complete, working AES-GCM implementation.

Failure contract

If unwrap throws a SerializationException, an IllegalStateException, or an IllegalArgumentException, the failure surfaces as a DocumentDecodingException. See Error Handling.
