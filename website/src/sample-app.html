Sample App

A runnable Compose Multiplatform sample lives in the repository's sample/ folder. It runs on both Android and iOS. It is made of three parts:

  • sample/shared/ holds one shared UI and the business logic for both platforms.
  • sample/androidApp/ is a thin Android wrapper.
  • sample/iosApp/ is a real Xcode project that embeds the shared Kotlin framework through Gradle's embedAndSignAppleFrameworkForXcode task. The sample itself does not use CocoaPods.

What it does

A home screen lists five use cases. Each one is a real, working screen backed by the real Documents API:

  • Settings & Preferences. Typed, observable app settings. A SettingsRepository wraps Documents.document<AppSettings>("app-settings") and uses the field() and fieldFlow() delegates for theme (SYSTEM, LIGHT, or DARK) and locale. Changing either one is saved instantly and updates the screen's own live readout, with no manual refresh.
  • Session & User State. Signing in and out, with an encrypted auth token. A SessionRepository opens Documents.collection("session"), which is configured with a real FieldDecorator (AesGcmFieldDecorator, using AES-GCM from cryptography-kotlin) that wraps authToken. The "Prove authToken is encrypted at rest" action opens a second document with a different AES key and shows the decrypt failure. This is concrete proof that the stored bytes are ciphertext and not the plaintext token.
  • Caches & Drafts. A draft that survives a relaunch, kept in its own store. A CacheRepository opens Documents.collection("cache"), which holds SyncState and DraftPost. The draft text field saves on a debounce and restores when you open the screen. A check on the same screen shows that the theme value from the Settings screen, which is in a different collection, stays untouched when "Clear cache" runs.
  • Reactive UI State. A simulated download that drives a live progress bar. A coroutine ticker repeatedly calls update(DownloadState::bytesDownloaded, bytesSoFar). A LinearProgressIndicator re-renders only because it collects the document's flow(). There is no polling, and the progress bar does not know where the write came from.
  • Shared KMP Persistence. One offline queue, with identical code on both platforms. A PendingRequestQueue wraps Documents.document<QueueState>("pending-requests"). The queue's items live inside a small wrapper class and not in a bare List document. See Opening Documents for why. The screen has "Enqueue mock request" and "Clear queue" actions and a live list. All of its code is in commonMain. Nothing platform-specific was written to make it work on both Android and iOS.

Run it

Clone the repository, then follow the steps for your platform:

  • Android. Run the sample/androidApp module from Android Studio or with Gradle.
  • iOS. Open sample/iosApp/iosApp.xcodeproj in Xcode and run it.

See Use Cases for the documented pattern that each screen demonstrates.
