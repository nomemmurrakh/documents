Opening Documents

Documents is the entry point. You can open a document directly on the default store, or open a named Collection first when a group of documents needs its own MMKV file.

The default store

Documents.document<T>(key) is the common case. It gives you the document stored under key in the default store, and it needs no configuration:

@Serializable
data class Note(val title: String = "", val body: String = "", val done: Boolean = false)

val note = Documents.document<Note>("note-1")

Opening a document does not write anything. It only gives you a handle to whatever is stored under that key, so note.get() returns null until something has been written.

You can pass an optional configuration block. It has two settings:

  • dispatcher is the dispatcher used to collect flow() and stateFlow(). See Reactivity.
  • decorators is a list of FieldDecorators applied to every field of this document. See Field Decorators.
val note = Documents.document<Note>("note-1") {
    dispatcher = Dispatchers.Default // this is already the default
}

Collections: a separate MMKV file

Use Documents.collection(name) only when a group of documents needs its own file. Typical reasons are a cache that is wiped on logout, data scoped to one user, or an encryption boundary:

val drafts = Documents.collection("drafts") {
    dispatcher = Dispatchers.Default
}
val draft = drafts.document<Note>("draft-1")

Every collection, including the default store, can only be used from one process. See Collections & Testing for details.

Opening the same document more than once

Opening a document is cheap, and you can do it as often as you like. You do not need to keep one instance and pass it around. All instances of the same document on the same store behave as one document:

  • A write through one instance shows up in flow() on the others.
  • If two instances call update at the same moment, the changes are applied one after the other, so neither is lost.

Dependency injection is still a good way to organize your code, but your data stays correct without it. The Reactivity Model explains how this works.

Each instance has its own configuration. The dispatcher can differ between instances. Use the same decorators for every instance of a document, because the bytes written by one instance must be readable by the others.

What T can be

T must be a @Serializable class, an enum, or a primitive. It cannot be a top-level List or another collection type. Each stored value is keyed by one of the type's declared properties (see Field Decomposition), and a bare list has no properties. Opening Documents.document<List<T>>(key) throws DocumentDecodingException immediately. A list works correctly as a field inside a class, so wrap it:

@Serializable
data class QueueState(val items: List<OfflineQueueItem> = emptyList())

val queue = Documents.document<QueueState>("pending-requests")

See Declaring Data Classes for which fields need a constructor default or a nullable type to stay safe under update().

The reserved key separator

Internally, every document is split into one stored key per field, named {document}::{field} (see Field Decomposition). Because :: is reserved for this, a document key that contains it is rejected with an IllegalArgumentException. Choose ordinary identifiers such as "note-1" or "user".

No setup needed

MMKV initializes itself the first time it is needed. On Android this happens through androidx.startup, and on iOS through an internal call that uses the app's sandbox path. You never call MMKV.initialize() and never pass a Context. The first call to Documents.document(...) or Documents.collection(...) is enough.

Note

On Android, this relies on a <provider android:name="androidx.startup.InitializationProvider"> entry that is merged into your app's manifest. Leave it alone. If you remove or override it, for example with a conflicting tools:node="remove", MMKV stops initializing and document access fails at runtime.
