Reactivity

A document exposes its changes as a Flow. Your UI, or any other code, can react every time the stored value changes. There is no polling and no need to read the value again yourself.

note.flow(): Flow<Note?>                  // cold: the current value, then every committed write
note.stateFlow(scope): StateFlow<Note?>   // hot: shared while there are subscribers

flow()

flow() is cold, so nothing happens until you collect it. When you do, it gives you the current value straight away, and then a fresh value after each committed write. Rapid writes are conflated, so you may see only the latest value. A write to a different document does not wake this flow up. When the document is deleted, the flow emits null:

note.flow().collect { current ->
    editor.render(current)
}

stateFlow(scope)

stateFlow(scope) is hot. It needs a CoroutineScope, and it holds the latest value so you can read it at any time. While at least one collector is subscribed, all of them share the same stream. This suits a stream owned by a ViewModel that should outlive any single collector.

Straight into Compose

val current by note.flow().collectAsStateWithLifecycle(initialValue = note.get())

current is nullable. A value of null means the note has not been written yet.

How it works under the hood

MMKV has no built-in way to listen for changes, so reactivity is handled inside your process. Every store has one change bus. After each committed write or delete, the library puts the affected document's key on that bus. flow() listens for its own key and reads the document again when it sees it.

The bus belongs to the store, so separate instances of the same document stay in sync. See Reactivity Model for the full mechanism. It also explains why changes made by another process are not detected.
