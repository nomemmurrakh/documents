Error Handling

get() and field reads throw a DocumentDecodingException when a stored field cannot be decoded. You never get a bare, low-level exception from the serialization layer.

try {
    val current = note.get()
} catch (e: DocumentDecodingException) {
    log.warn("note-1 field '${e.field}' failed to decode", e.cause)
}
Note

In practice this is rare. It only happens if a stored field is genuinely corrupted, or was written by an incompatible older version of your app. You do not need a try/catch around every get() call. Catch it at a boundary that already handles unexpected failures, such as a repository layer or a top-level error handler.

What it wraps, and why

A document is stored as one MMKV key per field (see Field Decomposition). So a single field can go bad, for example through a corrupted byte range or a stale format from an old app version, while every other field in the same document stays healthy.

DocumentDecodingException tells you which document and field failed:

  • documentKey is the key of the document.
  • field is the field that failed, when there is one.
  • cause is the underlying exception.

Without it, the underlying cause would surface as a bare SerializationException, IllegalStateException, or IllegalArgumentException from the CBOR format. Wrapping them means your code catches one library exception type and does not need to know about the serialization layer's own errors.

A configured field decorator can fail too. If its unwrap throws one of those three exception types, for example because of a wrong key, corrupted ciphertext, or a failed integrity check, the failure is wrapped in the same way. It looks like any other decode failure.

What is not an error

A document that was simply never written is not a decoding failure. get() returns null in that case. See Read & Write.

What each message means

A DocumentDecodingException has one of four messages. Each one starts differently and says what to do:

  • "Cannot update document 'note' because it has not been written yet…" The first update() ran on a document that was never written, and a field has no constructor default and is not nullable. Give the field a default, make it nullable, or call set() first. See Declaring Data Classes.
  • "Document 'note' is missing a stored value for required field 'title'…" A stored document has no value for a required field. It was probably written by a different version of your data class. Give the field a default or make it nullable so older data still loads.
  • "Field 'title' of document 'note' could not be read as kotlin.String…" The stored bytes are corrupted, or were written by an incompatible version of your data class.
  • "A field decorator failed to unwrap field 'authToken'…" A FieldDecorator threw while reading. Check that the decorators, their order, and any keys match the ones used when the value was written.

The last two messages include the name of the underlying exception, such as SerializationException, but not its text. A decoder error can quote stored data, and a stored value must not end up in a log. The full exception is on cause if you need it.
