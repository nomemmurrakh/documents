Declaring Your Data Class

Every Document<T> is backed by an @Serializable class that you write. Each property can be nullable or not, and can have a constructor default or not. Some combinations compile fine but crash at runtime, for example on a button tap. This page explains which ones and how to avoid them.

The rule

Documents never invents a value for a field. It only uses one of two sources: a value you already stored, or a default you already declared in the constructor. If neither exists, it fails loudly instead of guessing. There is no correct placeholder the library could make up for a field such as title: String or count: Int.

@Serializable
data class Note(val title: String = "", val count: Int = 0) // safe: every field has a default

Give every field in a document type either a constructor default or a nullable type (= null). A field with neither is only safe if you are certain the document is always written with set() before it is ever changed with update().

Why this matters: update() on an absent document

update { current -> ... } needs a starting value to run the builder on. If the document already exists, that value is the current one. If nothing has ever been written for this key, the starting value is built by decoding the type as if every field were absent. That only works for fields that have something to fall back on:

  • The field has a constructor default, for example val count: Int = 0. The default is used. This works.
  • The field is nullable and has no default, for example val nickname: String?. It becomes null. This also works, because being nullable is already a fallback.
  • The field is non-null and has no default, for example val title: String. There is nothing to fall back on, so update() throws DocumentDecodingException.

The rule is the same for a String, an Int, a nested @Serializable type, or an enum. The library cannot know which value you consider correct for a required field, so it never guesses.

A first-run crash, concretely

This type looks reasonable and compiles fine:

@Serializable
data class Note(val title: String, val count: Int) // no defaults, both non-null

It works perfectly with set() and get(). But if you call update() before the document has ever been written, it crashes. This can happen on the very first button tap in a fresh app install, when you increment a counter:

val document = Documents.document<Note>("note")

// Crashes if "note" was never set() before: there is no stored title
// and no default to fall back to.
document.update { it.copy(count = it.count + 1) }
com.nomemmurrakh.documents.DocumentDecodingException: Failed to decode field 'title' of document 'note'
Note

This message is more generic than it should be. It reads the same as the message for a genuinely corrupted field (see Error Handling), even though this case has a known cause: a missing constructor default. A clearer message for this specific case is planned. Until then, if you see DocumentDecodingException the first time you call update() on a document, suspect a missing default before you suspect corrupted data.

How to fix it

Use any one of these:

// Give every field a constructor default
data class Note(val title: String = "", val count: Int = 0)

// Or make the field nullable, which defaults to null
data class Note(val title: String?, val count: Int = 0)

// Or guarantee set() runs before update() ever does
document.set(Note(title = "Untitled", count = 0))
document.update { it.copy(count = it.count + 1) } // safe now

Defaults and nullability

A field counts as having a fallback in two cases. Either the constructor gives it a default value, or its type is nullable, because null is then a valid fallback. These two options are independent. A non-null field is safe if it has a default, and a nullable field is safe even with no default. Pick whichever reads better for what the field means.
